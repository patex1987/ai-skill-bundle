# Closing the catalog's missing post-implementation memory

The catalog is stronger than the leading repos on the part of the workflow they treat loosely, namely human-agreed gates before and after coding, and weaker on the part they handle best: remembering what was actually built. Its distinctive strengths are acceptance tests agreed with the user before any production change, a written annotation cycle on the plan, an independent validation step, and tier-based model routing rendered to four tools. Matt Pocock's skills, obra/superpowers and GSD have no equivalent of the first two, and none of the three has the render pipeline. But the catalog has no record of the system's state after implementation, no plan lifecycle status, no ADR practice, no debugging skill, and no switch that lets the user choose fresh-context subagents per phase. GSD is the only peer with a developed post-implementation record (per-plan SUMMARY.md rolled into STATE.md and PROJECT.md), and it is widely criticised as heavy; OpenSpec is the only one that keeps a deterministic current-state tree (`openspec/specs/`), but it cannot verify that the tree matches the code. The highest-value gap is therefore a small, human-gated "close-out" step after `plan-validation` that records the as-built delta, promotes surviving decisions, and updates one current-state document. OpenSpec is best treated as a candidate storage format to trial in a scratch repository, not as a dependency to adopt now, because the integrations reported in the field fail when two tools both own a plan. Evidence quality is uneven, and the caveats below matter for how far each recommendation can be pushed.

## The catalog leads on human gates and trails on memory and isolation

The catalog's `core` pack ships one skill per phase (codebase-research, external-research, principal-engineer-planner, plan-execution, plan-validation, model-routing) plus the `scout` and `check-runner` helpers. Phases hand off through Markdown under `docs/research`, `docs/plans`, `docs/validation` and `docs/reviews`, and the plan file is "the shared state that survives context compaction" ([docs/workflow.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/docs/workflow.md)). The planner refuses to finalize without acceptance scenarios the user has actually agreed to, and says silence or an agent-written status does not count ([principal-engineer-planner SKILL.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/catalog/skills/principal-engineer-planner/SKILL.md)). `plan-execution` then runs a vertical-slice loop that requires the baseline test to fail for the intended reason, and `plan-validation` separates execution-reported evidence from validator-verified evidence.

Set against the peers, this combination is rare. Superpowers has a hard approval gate on the design doc and a plan-review gate, but the review is a chat approval of a linked file with no annotation protocol, and the agent authors the tests inside the plan rather than agreeing them with the user ([superpowers writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)). Pocock substitutes interactive "grilling" and quiz-the-user checkpoints for annotation, and the research found no annotate-the-document step in any repo it read ([Pocock ask-matt](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/SKILL.md)). GSD's human gates are the discuss conversation and end-of-phase UAT, again not inline plan markup ([GSD ARCHITECTURE.md](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/docs/ARCHITECTURE.md)). The annotation cycle is therefore a differentiator to keep, not a gap to close.

Three local findings qualify the lead. First, behaviour in real sessions is stated as not evaluated, and only the planner's review mode and `pr-walkthrough` ship eval fixtures, while `plan-execution`, `plan-validation` and `codebase-research` have none ([README.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/README.md) line 173). Superpowers, by contrast, publishes blind-graded counts for behaviour changes (brainstorming skipped the design doc in 24 of 24 runs before v7.0.1 and 3 of 24 after), though these are author-reported ([Superpowers release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). Second, Superpowers enforces a size test because Claude Code truncates re-attached skills at 20,000 characters after compaction; the catalog's planner `SKILL.md` is 14,889 bytes, so it is under that line but has little room to grow, and the catalog has no equivalent test. Third, the catalog has no debugging skill, whereas both Pocock (`diagnosing-bugs`, which refuses to hypothesise until one red-capable command exists) and Superpowers (`systematic-debugging`, "no fixes without root cause investigation") treat it as core ([Pocock diagnosing-bugs](https://github.com/mattpocock/skills/blob/main/skills/engineering/diagnosing-bugs/SKILL.md), [Superpowers systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)).

The Reddit thread could not be fetched, so the "top 10 fastest-growing Claude skill repos, October 2026" was first reconstructed from a GitHub issue that quotes the skillleaderboard.com ranking ([dzaffren/claude-plugin#112](https://github.com/dzaffren/claude-plugin/issues/112)). The author has since supplied the post's screenshot (skillleaderboard.com, October 1-31, 2026), and it matches the reconstructed names, ranks and star gains exactly, so the list is confirmed; only the post's own text and comments remain unseen. More important for the brief, that list does not contain GSD or OpenSpec. Of the repos you named, only Pocock (rank 1) and Superpowers (rank 8) appear; the other entries are ponytail, Cloudflare's security-audit skill, impeccable, anatomy, diagram-design, graphify, taste-skill and hallmark. Five of those eight are front-end or visual-output skills with little bearing on a research-to-validation catalog, so GSD and OpenSpec are compared here on their own merits rather than as list entries.

GSD needs two warnings. The `gsd-build/get-shit-done` repository is archived and now a 12-line redirect to `open-gsd/gsd-core`, so "current GSD" means GSD Core 1.20.x, and the file-level detail below describes the pre-fork design at commit `bdcaab2` ([open-gsd/gsd-core](https://github.com/open-gsd/gsd-core/blob/main/README.md)). A fork maintainer's README commit claimed the original maintainer had been unreachable since 2026-04-01 and linked a project token to a rug-pull. That claim is corroborated only by that commit and one aggregator whose page returned 403, and the researchers did not check npm for tampering; treat "compromised" as unverified and "archived and moved" as confirmed ([AI Weekly](https://aiweekly.co/alerts/get-shit-done-creator-rug-pulls-gsd-token-vanishes)). GSD's criticism is likewise anecdotal: the Hacker News thread (473 points) mixes reports of burned usage limits and hours-long runs with praise from users on complex greenfield work, and no controlled token benchmark exists ([HN 47417804](https://news.ycombinator.com/item?id=47417804)).

The OpenSpec findings come from docs, schema files and source code, not from a run: the CLI install was denied in the research session, so claims such as "a proposal-light change passes `validate` and `archive`" are untested ([OpenSpec docs/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)). The Working Backwards fit-and-risk analysis is the thinnest part of the research: a usage limit cut off the search for independent critiques, so the claim that PR/FAQ is ceremony for refactors and infrastructure rests on the skills' own anti-pattern text and on inference, and no evidence shows that a PR/FAQ-first step improves agent plan quality. The ADR and Mermaid notes were also partly rate-limited; Nygard's original post was not re-fetched, and `mmdc` exit codes on syntax errors were never tested. Popularity figures for skills such as the PR/FAQ ones reflect host repositories, and vendor benchmarks (ponytail's, Graphify's) are self-reports.

## Post-implementation records: peers mostly lack one, and OpenSpec's version has a hard limit

The research question here has a blunt answer for three of the four peers. Superpowers deletes its run workspace on a clean final review ("the git history is the record now") and surfaces mid-run rulings only in the final chat message ([final-review.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)). Pocock writes glossary entries and ADRs inline during grilling, offers a PR template with evidence and "merge danger", and runs `/retro` to improve the agent environment, but has no skill that updates documentation after a feature ships ([Pocock retro](https://github.com/mattpocock/skills/blob/main/skills/engineering/retro/SKILL.md)). The catalog is in the same position: plans stay in `docs/plans/` with no status field, and the only "implemented" marker found is a hand-written line in one plan that points to `docs/REVIEW-LOG.md` ([typescript-naming-cohesion-validation.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/docs/plans/typescript-naming-cohesion-validation.md)). Its plans are revision-pinned snapshots, so nothing tells a later session whether a plan was implemented, abandoned or merely proposed. Execution evidence has no defined file either: `plan-execution` says "the plan or its execution log" and `plan-validation` says "established plan/log or `docs/validation/<task>.md`".

GSD is the model for what a developed record looks like. The executor writes a per-plan SUMMARY.md with machine-readable frontmatter (`provides`, `affects`, `key-decisions`, `requirements-completed`), a task-commit table, a "Deviations from Plan" section and a self-check ([GSD templates/summary.md](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/get-shit-done/templates/summary.md)). A transition step then edits PROJECT.md in place, moving shipped requirements to "Validated" and logging decisions, and a drift gate compares the codebase map's `last_mapped_commit` with HEAD ([GSD transition.md](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/get-shit-done/workflows/transition.md)). Two design choices transfer cleanly. A cheap structured index (`history-digest` over SUMMARY frontmatter) lets later planning load only two to four relevant prior records, and the verifier is told not to trust SUMMARY.md because it "documents what Claude SAID it did" ([GSD gsd-verifier](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/agents/gsd-verifier.md)). The cost is the ceremony users complain about, and the catalog's explicit annotate and agreed-acceptance steps already do some of the work GSD's compensating gates do.

OpenSpec offers a different answer: `openspec/specs/<capability>/spec.md` holds current agreed behaviour as requirements with Given/When/Then scenarios, and archiving a change merges delta files (applied in the order RENAMED, REMOVED, MODIFIED, ADDED) into that tree before moving the change to `archive/YYYY-MM-DD-<name>/` ([specs-apply.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/specs-apply.ts), [concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). Its limits are the crux for your integration question. Nothing machine-checks that specs match code, and even `/opsx:verify` is an LLM search that does not block archive. The spec step is the one that gets skipped: issue #1212 showed a change that was "fully implemented, tested, and archived" while `openspec/specs/` stayed out of date with no warning, mitigated in July 2026 by requiring deltas or an explicit `skip_specs` opt-out ([issue #1212](https://github.com/Fission-AI/OpenSpec/issues/1212)). The project itself warns against back-filling existing code because "those specs go stale, because nothing forces them to track reality" ([existing-projects.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)).

**Lightest integration.** The least invasive design keeps `docs/research/*.md` and `docs/plans/<feature>.md` exactly as they are and uses OpenSpec only for the post-implementation tree. After `plan-validation` passes, a fresh-context agent reads the plan's acceptance list, the diff and the tests and writes delta specs per affected capability, with the plan's AC IDs as stable scenario names (they are the merge key for MODIFIED blocks), plus a short `proposal.md` that points at the plan instead of restating it. `openspec validate --strict` and `openspec archive --yes` then do the merge. A `.openspec.yaml` `x-*` key can carry the plan link, because OpenSpec ignores those keys. This is the researchers' inference, not a documented procedure, and it is untested.

**Duplicate-plan risk.** Duplicate plans are the failure the field reports describe, so the design should avoid them by construction. In one hands-on test of three OpenSpec and Superpowers connection points, two failed: `writing-plans` ignored `tasks.md` and produced its own seven-task plan, so two task lists never synced ([besthub.dev](https://besthub.dev/articles/openspec-superpowers-integration-3-connection-points-tested-2-failed-a-hands-on-review-46e64163b70d), single-author secondary source). Another write-up reports a 60-line `tasks.md` against a roughly 1,300-line Superpowers plan ([austinxyz blog](https://austinxyz.github.io/blogs/blog/openspec-superpowers-combined)). The rule that follows is to never let OpenSpec generate `design.md` or `tasks.md` in this setup, since they duplicate the plan's Design and Steps sections. A residual risk stays: writing specs after the fact moves drift from "spec written before code" to "agent describes what it intended rather than what exists", which only a fresh-context reviewer comparing delta to code can mitigate.

**Install and fit risks.** OpenSpec writes into `.claude/skills/`, `.agents/skills/` and per-tool command folders, which the `.ai/` renderer owns, so `openspec init --tools none` or a scratch repository is the safe first step; the `--tools none` plus manual copy path is itself undocumented. It requires Node 22.12 or newer for npm installs. Its cross-repo "stores" feature is still beta ("command names, flags, file formats, and JSON output may still change"), so with a multi-repo platform the lower-risk choice is one `openspec/` per repository ([stores beta guide](https://github.com/Fission-AI/OpenSpec/blob/main/docs/stores-beta/user-guide.md)). My assessment is that the format is worth borrowing before the tool is worth adopting: a hand-maintained `docs/specs/<capability>.md` using Requirement/Scenario blocks costs nothing and avoids the dependency, install collision and beta risks, at the price of losing the automatic delta merge. Decide between format-only and the CLI after a scratch trial answers whether `validate` and `archive` accept a proposal-light change and whether a schema can omit `tasks`.

**Record-state step design.** Whichever store is chosen, the missing capability is the same: a close-out step that (a) sets plan status and records the as-built delta against the plan, (b) filters the plan's Decisions list through a significance gate into ADR candidates, and (c) updates one current-state document. Keeping the three jobs separate matters because they answer different questions: the spec or architecture overview says what the system does now, ADRs say why, and the plan says what was intended. The OpenSpec design.md problem shows what happens otherwise: archived design reasoning is not merged forward ([OpenSpec concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md); [intent-driven.dev](https://intent-driven.dev/blog/2026/04/29/spec-driven-development-with-adr/)). A cheaper complement from outside the main five is ponytail's `shortcut: <limit>, <when to upgrade>` code comments, aggregated into a debt ledger by a read-only skill, which gives a post-implementation record derived from code rather than a separate document ([ponytail AGENTS.md](https://github.com/DietrichGebert/ponytail/blob/main/AGENTS.md)).

## Fresh-context isolation: the peers offer switches, the catalog offers prose and a closed schema

The three peers handle the choice differently, and the differences map to who decides. Superpowers lets the user choose at plan handoff: writing-plans asks them to review the plan and pick "Subagent-driven" (fresh implementer per task plus a fresh reviewer, "most thorough") or "Native" (implement inline, then one fresh whole-branch reviewer on the most capable model, "cheapest and fastest"), and the agent must recommend one with a reason ([writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)). That choice has a history: v5.0.0 made subagent-driven mandatory, and v6.4.1 restored the two-way choice ([release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). Subagents never inherit session history; they receive a brief file extracted from the plan, and the implementer writes its report to a file and returns only status, so the controller never pastes diffs ([subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). Research gets no subagent, and planning gets one only in brainstorming's "builder check".

GSD makes nearly everything a config toggle. Every spawned agent gets a clean context window (researcher, planner, plan-checker, executor, verifier), orchestrators pass file paths rather than content, and `.planning/config.json` carries `workflow.research`, `plan_check`, `verifier`, `parallelization.*`, `use_worktrees`, `model_profile` and per-phase model overrides, all "absent = enabled" ([GSD CONFIGURATION.md](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/docs/CONFIGURATION.md)). Lightweight paths exist as commands: `/gsd-quick` (shorter path, same system) and `/gsd-fast` (inline, no subagents). The defaults are the heavy ones, which is the root of the cost complaints, and on runtimes without an Agent tool it degrades to sequential inline execution, undercutting the isolation claim there ([execute-phase.md](https://github.com/gsd-build/get-shit-done/blob/bdcaab2/get-shit-done/workflows/execute-phase.md)).

Pocock handles it by rule and by command. His AGENTS.md requires every skill that dispatches a subagent to say "start it with a fresh context window", because some harnesses such as Codex fork the parent conversation by default ([Pocock AGENTS.md](https://github.com/mattpocock/skills/blob/main/AGENTS.md)). `/research` runs as a background fresh-context agent writing one cited Markdown file, and the user selects the execution style by choosing `/implement` in one window or `/implement-spec`, which runs a fresh implementer per ticket in its own worktree. His `PHASE-BOUNDARIES.md` gives an ordered decision tree at each boundary: continue, then clear, then handoff, then subagent, and compact only as the default last resort, justified by the idea that summarising turns a session into a lossy secondary source ([PHASE-BOUNDARIES.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/PHASE-BOUNDARIES.md)). Keeping grill, spec and tickets in one unbroken window is explicit, which matches the catalog's own "one session" guidance rather than contradicting it.

What the catalog can express today is narrower. `docs/workflow.md` tells the user to keep research, planning and implementation in one session, and only `plan-validation` requires an independent context, scoped to risky slices ([plan-validation SKILL.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/catalog/skills/plan-validation/SKILL.md)). The `bundle.json` schema is closed: install fails on any top-level key outside `schema_version, packs, local, targets, routing, invocation` and the `skills|agents|rules` add/remove objects ([scripts/aibundle.py](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/scripts/aibundle.py)). The per-repo levers that exist are `invocation` (auto or explicit), `routing.apply|models|overrides`, `.ai/overlays/<skill>.md` (read first and "takes precedence") and `.ai/project-guidance.md`. `metadata.context: fork` makes a skill run in its own subagent and is allowed in catalog frontmatter, but no catalog skill sets it, it is static at catalog level rather than repository-selectable, and the repository documents it only for Claude Code ([tool-mechanics.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/catalog/skills/model-routing/references/tool-mechanics.md), vendor facts checked 2026-10-23 and not re-verified here). The portable primitive across Claude Code, Codex, Cursor and Gemini is the rendered agent file, and Codex pins the model in that file so a deep-tier escalation at spawn time does not work.

That gives three homes for a "phase isolation: inline or delegated" setting, in increasing cost. An overlay per skill needs no code but needs each skill's text to say "unless the overlay says otherwise", and the setting is unvalidated prose spread over several files. `project-guidance.md` is one always-loaded place but equally unvalidated. A new `workflow` key in `bundle.json` would give validation and a single home, consistent with how `invocation` and `routing` already work, but requires changes to `aibundle.py` (allowed set and type check), `render.py` (`load_config` and `render_index`, since skills have no other way to see the manifest), the README and tests. My judgement, from the evidence: research is the best candidate for delegation because its output is already a file and its search noise is pure cost (Pocock and the catalog's own `scout` agree), planning is the worst because annotation depends on shared context, and execution per slice is where both Superpowers and Pocock isolate. Start with the overlay route to learn which choices the author actually flips, then promote to `bundle.json` only if two or more repositories use it. Whatever is chosen should ship with a stated default, since Superpowers' own numbers (all 26 reviewers on the top tier before it required a model field; roughly 2x faster and almost 50 percent fewer tokens after, author-reported) show that unmanaged delegation is expensive.

## Customer-first, ADR and diagram skills: one is worth building first

**Working Backwards.** No official Anthropic or Amazon skill exists; the research found no mention of PR/FAQ in `anthropics/skills` or in Pocock's repository. The best-engineered option is BMAD's `bmad-prfaq` (five stages, concept-type calibration for internal tools, a distillate for downstream requirements), but it is coupled to BMAD's `_bmad/` runtime and would need reimplementing ([bmad-prfaq](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-prfaq/SKILL.md)). Lighter options are Product-Manager-Skills' press-release skill (7.9k stars, explicitly "not for trivial features") ([press-release](https://github.com/deanpeters/Product-Manager-Skills/blob/main/skills/press-release/SKILL.md)), Amplitude's single prompt with a kill test and a mandatory unanswered internal-FAQ question ([amazon-working-backwards](https://github.com/amplitude/builder-skills/blob/main/product-skills/skills/amazon-working-backwards/SKILL.md)), and robdefeo's two-phase skill that makes the "Five Questions" a standalone first phase ([robdefeo](https://github.com/robdefeo/agent-skills/blob/main/skills/amazon-working-backwards/SKILL.md)). Amazon's own constraints are the main lever for a light version: the press release is under one page, the FAQ at most five, and the document is a go/no-go before building, with most PR/FAQs never becoming products ([Amazon](https://www.aboutamazon.com/news/workplace/an-insider-look-at-amazons-culture-and-processes)). The "five questions" label is attributed to Bryar and Carr only by secondary sources; Amazon's pages and workingbackwards.com list seven reviewer criteria instead, so a catalog skill should describe them as commonly cited, not quote the book ([workingbackwards.com](https://www.workingbackwards.com/concepts/working-backwards-pr-faq-process/)).

On fit, the hedged position is this. The method suits new user-facing capabilities and anything where a solution is posed as a problem ("we need X"); in this platform the "customer" of a recommendation API or MCP tool surface is the consuming service or agent. It is ceremony for refactors, dependency upgrades, CDK changes with no new consumer-visible behaviour, and bug fixes with a repro. The named risks are invented quotes and metrics, structured artifacts "resting on invented numbers" when one user and a model replace the room, gate fatigue on small work, and a second source of truth that drifts from the plan ([siddarthnyati README](https://github.com/siddarthnyati/working-backwards/blob/main/README.md)). Pocock's `to-spec` already writes problem and solution "from the user's perspective" with a long user-story list, and Superpowers' brainstorming asks a why-first question and sizes the output, so the catalog planner's "who benefits" restatement is partly covered. The thin evidence base argues for the cheapest form first: a "customer lens" substep in the planner for user-facing work (Five Questions in five to eight lines, each answer tagged observed, reported, assumed or unknown, plus an internal-FAQ list with at least one unanswered item), before any separate `customer-brief` skill writing `docs/briefs/`. If a separate skill follows, requirements should carry a `Source:` pointer to the brief and unsourced requirements should be flagged as scope additions, a traceability device from the heaviest of the skills read.

**ADR.** Formats converge on Nygard's five fields or MADR 4.0.0 (released 2024-09-17, with minimal and bare variants), usually at `docs/adr/NNNN-slug.md` with a status of proposed, accepted, deprecated or superseded ([MADR](https://adr.github.io/madr/)). The sharpest agent-appropriate design is Pocock's: write an ADR only when the decision is hard to reverse, surprising without context, and the result of a real trade-off, create the directory lazily, and allow a one-paragraph body ([ADR-FORMAT.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/ADR-FORMAT.md)). The most complete workflow is the everything-claude-code skill: approval before writing, an index, and a read mode, though its broad category list ("Process", "Testing") invites spam ([ECC SKILL.md](https://github.com/affaan-m/everything-claude-code/blob/main/skills/architecture-decision-records/SKILL.md)). No surveyed skill ships a validation script or extracts ADRs from a finished plan's Decisions list, which makes that mode, filtered by the three-part gate and compared with the actual diff, a differentiator rather than a copy. Immutability needs a pragmatic rule: the ADR community says "in theory, immutability is ideal; in practice, mutability has worked better for our teams" ([Joel Parker Henderson](https://github.com/joelparkerhenderson/architecture-decision-record)), so allow only status changes, superseded-by pointers and dated notes. Numbered filenames collide in parallel worktrees, which log4brains cites as its reason for dropping them; that is an inference for agent-parallel work, not a tested claim. No empirical study of LLM-authored ADR quality was found.

**Mermaid.** Existing Mermaid skills are mostly syntax catalogs with per-type reference files and, in the cases read, no validation step ([WH-2099/mermaid-skill](https://github.com/WH-2099/mermaid-skill), [softaworks mermaid-diagrams](https://github.com/softaworks/agent-toolkit/blob/main/dist/plugins/mermaid-diagrams/skills/mermaid-diagrams/SKILL.md)). The unmet need is judgement and verification: when a diagram earns its place, which type answers which question, and a render check. Three facts shape any skill. Mermaid 12.0.0 (2026-09) was breaking: ELK became the default layout, the default theme and look changed, and `defaultRenderer` was removed, so older advice and diagrams render differently, and the current release is 12.3.0 ([mermaid 12.0.0 release](https://github.com/mermaid-js/mermaid/releases/tag/mermaid%4012.0.0)). `@mermaid-js/parser` does not cover flowchart, sequence, class, state or ER, so real validation means running `mmdc` (which needs headless Chromium) over each fenced block ([mermaid parser](https://github.com/mermaid-js/mermaid/tree/develop/packages/parser/src/language), [mermaid-cli](https://github.com/mermaid-js/mermaid-cli)). And the version GitHub renders is unknown; GitHub's docs only suggest rendering an `info` block to check ([GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)), so committed docs should stay on long-stable types. Chromium was absent where the research ran and `mmdc`'s exit code on a syntax error was never tested, so any validation script must degrade to static checks (known type keyword, lowercase `end`, unbalanced quotes, size limits of 50,000 characters and 500 edges) and say so. The strongest case for a diagram skill is as a companion to the close-out step, where a living `docs/architecture/overview.md` needs C4-style flowcharts edited in place. Without that anchor it is a convenience, since the model already knows the syntax. Visual skills in the top ten such as diagram-design (HTML and SVG, branded, "no Mermaid slop") serve a different purpose and add little here except the habit of asking whether the reader would learn more than from a paragraph ([diagram-design](https://github.com/cathrynlavery/diagram-design/blob/main/skills/diagram-design/SKILL.md)).

**Other gaps worth naming.** Pocock's `/retro` rule that a mechanical violation gets a deterministic check (lint rule, hook, CI) rather than another prose rule is echoed by Cloudflare's schema-validated findings and ledger validators, impeccable's 62 non-LLM rules, and Superpowers' tests ([Cloudflare security-audit-skill](https://github.com/cloudflare/security-audit-skill/blob/main/README.md)). The catalog's own model-routing "evidence loop" is explicitly unimplemented, with a recorder "not implemented here" ([docs/model-routing.md](/home/patex1987/development/movie-reservation-platform-lab/skill-bundle/docs/model-routing.md)). The catalog has no router skill kept in sync with its contents (Pocock's `ask-matt`, plus an AGENTS.md rule against "a router that lies"), though its workflow guide serves part of that role. It also has no ticket graph with blocking edges for parallel fresh-context execution, which Pocock's `/implement-spec` and GSD's waves provide; for a human-supervised workflow that is lower priority. Its authorization stance is a strength worth noting: GSD's pre-redirect README recommended `--dangerously-skip-permissions`, while the catalog separates test agreement, implementation authorization and merge authority.

## Conclusion

The comparison changes the question from "which framework should the catalog resemble" to "what does it need that no framework supplies". Pocock, Superpowers and GSD each optimise the front of the workflow and execution; the research found no peer that combines user-agreed acceptance tests, written annotation and independent validation, so the catalog should protect that combination, including from the pull of heavier pipelines. The sharpest finding is negative: the two largest repos by stars keep no durable post-implementation record, so the catalog is not behind a standard here but is missing an unsolved problem, and the available solutions (GSD's summaries, OpenSpec's archive) both carry known drift and ceremony costs. That argues for a small, human-gated close-out step designed around reconciliation against the code, not for adopting a whole spec framework.

Two things remain open that the notes cannot settle. The behaviour claims about OpenSpec's proposal-light flow, the Mermaid validation script and several tool-specific subagent mechanics are untested, so each recommendation that depends on them should begin with a scratch experiment. And star growth reflects marketing and newsletters as much as quality (Pocock's README cites a roughly 60,000-subscriber newsletter), so evidence from adoption is weaker than evidence from the mechanisms each repo documents; the follow-up Q&A should therefore start with candidates 1 to 3, whose answers decide the design of most of the rest.
