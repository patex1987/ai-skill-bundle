Version read: `main` at commit `22f0b46` (Release v7.0.2), dated 2026-11-03; `package.json` version 7.0.2. Repo had about 313.7k stars (GitHub API, 2026-11-07). I cloned the repo and read the SKILL.md files and supporting files directly. Base URL for all citations: https://github.com/obra/superpowers/blob/main/ (path appended). Releases seen via GitHub API: v6.0.3 (2026-06-18), v6.1.0, v6.2.0, v6.3.0 (2026-08-12), v6.4.1 (2026-09-19), v6.4.2 (2026-09-25), v7.0.0 (2026-10-10), v7.0.1 (2026-10-21), v7.0.2 (2026-11-03).

## 1. Full skill list and the workflow they form

### Takeaway
Superpowers is a 15-skill, auto-triggered pipeline: brainstorming (design doc, hard-gated approval) -> worktree -> writing-plans (file-based plan, user review and execution-mode choice) -> subagent-driven-development or executing-plans -> finishing-a-development-branch, with TDD, systematic-debugging, verification and code-review skills as cross-cutting disciplines. A SessionStart hook injects `using-superpowers`, which tells the agent to invoke any skill with a 1% chance of applying.

### Cited Findings
- The `skills/` directory has 15 skills: brainstorming, diagnosing-superpowers, dispatching-parallel-agents, executing-plans, finishing-a-development-branch, receiving-code-review, requesting-code-review, subagent-driven-development, systematic-debugging, test-driven-development, using-git-worktrees, using-superpowers, verification-before-completion, writing-plans, writing-skills — [skills/ tree](https://github.com/obra/superpowers/tree/main/skills); README "What's Inside" groups them as Testing / Debugging / Collaboration / Meta — [README.md](https://github.com/obra/superpowers/blob/main/README.md)
- README "Basic Workflow" ordering: 1 brainstorming, 2 using-git-worktrees (after design approval), 3 writing-plans, 4 subagent-driven-development or executing-plans, 5 test-driven-development (during implementation), 6 requesting-code-review (between tasks), 7 finishing-a-development-branch — [README.md](https://github.com/obra/superpowers/blob/main/README.md)
- `using-superpowers` is injected at SessionStart on startup, clear and compact via a hook; it says "If you think there is even a 1% chance a skill might apply... you ABSOLUTELY MUST invoke the skill", requires skill invocation before any response including clarifying questions, and contains a 12-row "Red Flags" rationalization table — [skills/using-superpowers/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md), [hooks/hooks.json](https://github.com/obra/superpowers/blob/main/hooks/hooks.json), [hooks/session-start](https://github.com/obra/superpowers/blob/main/hooks/session-start)
- Skill priority: process skills (brainstorming, systematic-debugging) come before implementation skills; "Before entering plan mode: if you haven't already brainstormed, invoke the brainstorming skill first"; user instructions (CLAUDE.md, AGENTS.md, GEMINI.md) outrank skills — [skills/using-superpowers/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md)
- brainstorming (rebuilt in v7.0.0, retuned in 7.0.1 and 7.0.2): asks what is known, looks at the project before asking, asks one open "why" question, plays back understanding in 200-300 word chunks, lays out 2-3 approaches in a separate message with a recommendation, sizes the work (small change gets a short design doc, project gets a full design), writes the design doc, runs a "builder check" subagent for projects, then requires approval and invokes writing-plans — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- brainstorming has an optional "visual companion" (a local web server serving mockups to a browser tab; offered just-in-time) — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [skills/brainstorming/visual-companion.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/visual-companion.md)
- brainstorming also allows a user-approved throwaway "spike" and a user opt-out ("just dive in"); a spike skips plan, implementation and review, and keeping its output "comes back through this gate" — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- using-git-worktrees: detect existing isolation first (compare `git rev-parse --git-dir` vs `--git-common-dir`, submodule guard), ask user consent before creating, prefer native harness tools (e.g. `EnterWorktree`), else `git worktree add` under `.worktrees/` (verify gitignored), run project setup, run baseline tests and ask if they fail — [skills/using-git-worktrees/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/using-git-worktrees/SKILL.md)
- finishing-a-development-branch: run full test suite (stop if red), detect environment, confirm base branch, present exactly 3 options (merge locally / push and open PR / keep as-is), or 2 on detached HEAD; discard only on explicit request and typed `discard` confirmation; worktree cleanup by provenance — [skills/finishing-a-development-branch/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/finishing-a-development-branch/SKILL.md)
- requesting-code-review: dispatches a `general-purpose` subagent from `code-reviewer.md` with description, plan/requirements, BASE_SHA and HEAD_SHA; Critical fixed immediately, Important before proceeding, Minor noted; "Push back if reviewer is wrong" — [skills/requesting-code-review/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md), [skills/requesting-code-review/code-reviewer.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md)
- receiving-code-review: six-step response pattern (read, understand, verify against codebase, evaluate, respond, implement one at a time); forbids performative agreement ("You're absolutely right!"); if any item is unclear, stop and ask before implementing any — [skills/receiving-code-review/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)
- dispatching-parallel-agents: one agent per independent problem domain (e.g. unrelated failing test files), with crafted context, not session history — [skills/dispatching-parallel-agents/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/dispatching-parallel-agents/SKILL.md)
- writing-skills: "Writing skills IS Test-Driven Development applied to process documentation" — pressure scenarios with subagents as tests, baseline failure first, then write the skill, then close loopholes — [skills/writing-skills/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- diagnosing-superpowers (new in v6.4.1): reads session transcripts to explain what went wrong (repeated work, ignored plan, skill not firing, surprising bill), reports with `path:line` evidence, can package a scrubbed bundle or draft a GitHub issue for user approval — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md), [skills/diagnosing-superpowers/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/diagnosing-superpowers/SKILL.md)
- Slash commands `/brainstorm`, `/write-plan`, `/execute-plan` were deprecated in v5.0.0 in favor of auto-triggered skills — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- There is no dedicated "research" or "annotate" skill, and no dedicated "validate" phase beyond verification-before-completion, per-task review, final review and the test-suite gate in finishing. Brainstorming's "Look Before You Ask" and "Do recon" paragraphs are the nearest thing to a research step, and they are conversational, not persisted — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)

### Inferences
- The mapping to the user's workflow is approximate: research ~ brainstorming recon (unsaved), plan ~ writing-plans, annotate ~ the "please review the plan" handoff (a chat approval, not an annotation protocol), implement ~ SDD or executing-plans, validate ~ verification-before-completion plus the final whole-branch reviewer plus finishing's green-suite gate.
- Superpowers is a "trigger by description plus bootstrap hook" design, so the pipeline order is enforced by cross-skill "REQUIRED SUB-SKILL" handoffs and by prose, not by any state machine.

### Gaps
- I did not read the full text of `visual-companion.md`, `writing-good-tests.md`, or every `systematic-debugging` support file; I did not fetch the author's blog posts (blog.fsck.com is only linked from the README).

## 2. Artifact formats and storage locations; plan granularity

### Takeaway
Design docs go in `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and plans in `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`, both committed. Plans have a fixed header (Goal, Architecture, Tech Stack, Spec link, Global Constraints, Review Focus) and a per-task structure (Files, Interfaces, checkbox steps). Since v6.4.2 plans record decisions (signatures, test assertions, exact values) rather than full code bodies. Run-time scratch (ledger, briefs, reports, diffs) lives in git-ignored `.superpowers/sdd/<plan-basename>/` and is deleted when the run finishes.

### Cited Findings
- Spec/design path: "in a software repo, `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed. Otherwise, pick a sensible place and say where. Your human partner's preferences override both." — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Design doc contents: intent and the why; goals, non-goals, anti-goals; constraints; approaches (2-3 ways considered, trade-offs, which the user picked and why); the parts of the how the user decided; what is left to the builder. A small change gets a short doc with the same points in a line or two each — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Directory layout introduced in v5.0.0 (2026-03-09): specs to `docs/superpowers/specs/`, plans to `docs/superpowers/plans/`; migration from `docs/plans/` suggested — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- The superpowers repo itself contains `docs/superpowers/specs/` with ~24 dated design docs (e.g. `2026-10-05-brainstorming-rebuild-design.md`) but no `docs/superpowers/plans/` directory in the current tree, and an older `docs/plans/` folder; so the maintainers' own plans are not kept in the repo in the documented location — [docs/superpowers/specs](https://github.com/obra/superpowers/tree/main/docs/superpowers/specs), [docs/plans](https://github.com/obra/superpowers/tree/main/docs/plans) (observed from the repo tree listing)
- Plan path: `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`; user preferences override — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Mandatory plan header: `# [Feature Name] Implementation Plan`, an "agentic workers" banner naming the required execution sub-skill and checkbox syntax, then **Goal**, **Architecture** (2-3 sentences), **Tech Stack**, **Spec** (path to the design doc), **Global Constraints** (project-wide requirements with exact values copied verbatim from the spec), **Review Focus** (up to five spec-implied failure modes no task tests exercise, each later pinned by a test in the owning task) — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Per-task structure: `### Task N: [Component]`, **Files** (Create/Modify with line ranges/Test), **Interfaces** (Consumes / Produces, exact signatures, because "A task's implementer sees only their own task"), then checkbox steps: write failing test, run (expect FAIL with message), implement, run (expect PASS), commit — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Step granularity: "Each step is one action with a checkable result." Task right-sizing: "the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate"; fold setup/config/docs into the task needing them — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Exact code vs decisions: a test step has the test name and assertions "as code, with the spec's exact values"; a code step has the exact signature, file and spec-pinned values, with a body "only for an algorithm the signature and tests do not determine"; a verification step has the command and the output that means pass. "A plan longer than the code it describes has written the code instead" — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- This is a change from earlier versions: v6.4.2 (2026-09-25) replaced "No Placeholders" with "What a Step Contains", replaced "zero context, questionable taste" with a capable-engineer reader, replaced "2-5 minutes" sizing with "one action with a checkable result", and added a proportion check (plan several times longer than the spec is a transcript). Motivation: frontier models over-implementing during planning; plans took a quarter of the time and about a third of the tokens in their repro — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- The README still describes the older format: "bite-sized tasks (2-5 minutes each). Every task has exact file paths, complete code, verification steps" and "enthusiastic junior engineer with poor taste, no judgement, no project context" — [README.md](https://github.com/obra/superpowers/blob/main/README.md). This conflicts with the current skill text above (stale README).
- Plan self-review (done by the planner itself, "not a subagent dispatch"): spec coverage, step scan, type consistency across tasks, Review Focus coverage, proportion — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Plan scope check: if the spec covers multiple independent subsystems, suggest separate plans, "each plan should produce working, testable software on its own" — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Run-time workspace: `bash scripts/sdd-workspace PLAN_FILE` creates a git-ignored directory `<repo-root>/.superpowers/sdd/<plan-basename>/` holding the ledger `progress.md` (first line `# SDD ledger — plan: <plan file path>`), task briefs (`task-N-brief.md`), implementer reports (`task-N-report.md`) and review packages (diff files). Helpers: `task-brief`, `review-package`, `sdd-workspace`, `sdd-repo` (SDD) and `task-start`, `task-done` (executing-plans) — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [skills/executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md), [skills/subagent-driven-development/scripts](https://github.com/obra/superpowers/tree/main/skills/subagent-driven-development/scripts)
- Ledger line formats: `Task <N>: complete (commits <base7>..<head7>, review clean)`, `Ruling: <what> — <why> — <cost if wrong>`, `Task <N>: minor (deferred): <one-liner>`, `Final: ...` — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [skills/subagent-driven-development/references/fix-loop.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/fix-loop.md)
- Pre-flight scan (before Task 1): a table written to the ledger with a row per pair of tasks sharing a file/interface and a row per task for self-consistency; conflicts ruled on with the spec as binding authority — [skills/subagent-driven-development/references/preflight.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/preflight.md)
- v6.0.3 moved scratch files from `.git/sdd/` to `.superpowers/sdd/` because Claude Code denies agent writes inside `.git/`; v6.2.0 made the workspace plan-scoped and deleted at end-of-life ("git history is the durable record") — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)

### Inferences
- The plan is a "decision list with exact interfaces and tests", closer to a contract than a code dump after v6.4.2, which narrows the gap with a plan format that only lists decisions and acceptance checks.
- The Spec link in the plan header plus Global Constraints is how the design doc "travels" to executors; it is the only link between design and implementation artifacts.
- There is no annotation format (comments, inline markers, numbered review notes) for the plan; review is a chat approval of a linked file.

### Gaps
- I did not inspect an actual real-world plan file produced by the current skill (none is in the repo); the format above comes from the skill's template.

## 3. Context isolation and subagent use; execution-mode choice; plan handoff

### Takeaway
Subagent-driven-development (SDD) gives each task a fresh implementer subagent and a fresh task reviewer, then one fresh whole-branch reviewer on the most capable model. Subagents get no session history; they get a brief file extracted from the plan. The user chooses at plan handoff between "Subagent-driven" and "Native" (inline) execution, and the agent is required to recommend one with a reason. Native mode still dispatches one fresh whole-branch reviewer.

### Cited Findings
- Core principle: "Fresh subagent per task + task review (spec + quality) + broad final review"; subagents "should never inherit your session's context or history — you construct exactly what they need" — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Per-task loop: record BASE sha, run `task-brief PLAN_FILE N` (extracts that task's full text to a unique file), dispatch implementer with: one line on where the task fits, brief path ("read this first — it is your requirements, with the exact values to use verbatim"), interfaces/decisions from earlier tasks, resolved ambiguities, report-file path. "Never make a subagent read the whole plan file." Do not paste prior-task summaries into later dispatches. Never run implementers in parallel — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Implementer prompt template: implement exactly what the task specifies, TDD if the task says so, commit, self-review (completeness, quality, discipline/YAGNI, testing), report as DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED; encouraged to ask questions before starting; "It is always OK to stop and say 'this is too hard for me'"; forbidden from dispatching subagents (esp. its own reviewer) — [skills/subagent-driven-development/implementer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)
- Implementer writes its full report to a file and returns only status, commits, a one-line test summary and concerns; the controller deliberately avoids pasting diffs or reports into its own context — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Task reviewer: one subagent per task returns two verdicts, spec compliance (Missing / Extra / Misunderstood) and code quality (separation of concerns, error handling, DRY, tests verify real behavior, file structure). It receives three paths (brief, implementer report, review-package diff file) plus global constraints; is read-only on the checkout; told "Do Not Trust the Report"; flags "Cannot verify from diff" items; cites file:line evidence — [skills/subagent-driven-development/task-reviewer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md)
- v6.0.0 (2026-06-16) merged the earlier two separate per-task reviewers (`spec-reviewer-prompt.md` and `code-quality-reviewer-prompt.md`) into one `task-reviewer-prompt.md`; README still describes "two-stage review (spec compliance, then code quality)" — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md), [README.md](https://github.com/obra/superpowers/blob/main/README.md)
- The controller may not coach the reviewer: "never instruct a reviewer to ignore or not flag a specific issue"; phrases like "do not flag", "at most Minor", "the plan chose" in a reviewer prompt are treated as pre-judging — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- Fix loop: triggered by spec failure, Critical/Important findings, or confirmed "cannot verify" gaps; max five rounds per task; rounds 1-3 resume the original implementer; rounds 4-5 dispatch a fresh implementer on a more capable model; each round ends with a scoped re-review (ADDRESSED / NOT ADDRESSED per finding); Minor findings go to the ledger, not the loop — [skills/subagent-driven-development/references/fix-loop.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/fix-loop.md)
- Final review: single whole-branch review on the most capable model, using `requesting-code-review/code-reviewer.md`; at most ONE fix subagent for the whole findings list, ONE scoped re-review, "no second fix wave" — residual findings go to the human at finish — [skills/subagent-driven-development/references/final-review.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)
- The reviewer prompt treats the spec as "a vision document": behavior the spec is silent on is judged by what a reasonable user expects; the reviewer lists a "Declined to judge" set the controller must rule on — [skills/requesting-code-review/code-reviewer.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/code-reviewer.md), [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md) (v6.4.1)
- User-selectable execution: after saving the plan, writing-plans asks the user to review the plan and "choose an execution method before implementation": **Subagent-driven** ("fresh subagent implements each task and a fresh reviewer checks it... Most thorough") vs **Native** ("I implement every task myself in this session... then one fresh reviewer on the most capable model checks the whole branch. Cheapest and fastest"). The agent must recommend one with a one-sentence reason drawn from the plan; if the user already supplied a method, it asks only for plan confirmation — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- History of that choice: v5.0.0 made SDD mandatory on subagent-capable harnesses and removed the choice; v6.4.1 (2026-09-18) rebuilt `executing-plans` as Native inline mode and restored a two-way choice — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- executing-plans (Native): implementer is the session itself; same workspace and ledger as SDD, "a plan can change executors mid-flight"; `task-start` prints brief path and BASE; every command step has an `Expected:` line to compare; plan-wrong deviations must be ledgered as a `Ruling:`; after all tasks one fresh whole-branch review (without a subagent tool: self-review, disclosed to the human as weaker); Critical/Important fixed in one pass, each fix RED->GREEN with a green suite and no re-review — [skills/executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)
- Both modes run continuously: "Do not pause to check in with your human partner between tasks." Only four things stop a run: irreversible/destructive operation, security-sensitive action, side effect outside the worktree that norms say to ask about (merge, push to shared branch, publish), or a plan "so broken that every path forward is a guess". Everything else is a "Ruling" logged in the ledger and reported at the end ("Rulings I made", "Deferred minors") — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [skills/executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)
- Model-tier routing exists inside SDD: "Use the least powerful model that can handle each role": cheap model for mechanical tasks (1-2 files, complete spec), standard for integration, most capable for architecture/design and the final review; reviewer model scaled to diff risk; fix-loop rounds 4-5 one tier above; "Always specify the model explicitly when dispatching" because omitted models inherit the session's expensive model. Counter-note: "Turn count beats token price" so mid-tier is the floor for reviewers and prose-spec implementers. The text uses generic tier words, not vendor model IDs — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- v6.0.0 reports that without a required model field, "one run put all 26 of its reviewers on the top tier"; their evals claim roughly 2x faster and almost 50% fewer tokens for the v6 flow (author's own measurement, "won't hold on every harness") — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- v6.4.1 adds opt-in nesting on Claude Code: the controller itself can run as a nested subagent on a mid-tier model (about half the cost and wall clock, per release notes) — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- The planning side also uses a fresh subagent: brainstorming's "builder check" sends the written design to a fresh general-purpose subagent that plays the builder and lists only the questions it would still need answered; the author sorts them into answered / minor (self-decided, marked) / theirs (one message to the user). Without a subagent tool the author reads the doc as that builder — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md), [skills/brainstorming/builder-check-prompt.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md)
- Writing-plans self-review is explicitly not a subagent dispatch (planner checks its own plan) — [skills/writing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)
- Codex mapping: needs `multi_agent = true`; spawn children with `spawn_agent {fork_turns: "none"}` for clean context; resume implementers with `followup_task` — [skills/using-superpowers/references/codex-tools.md](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/references/codex-tools.md)

### Inferences
- The strongest context-isolation idea is "hand artifacts as files, never paste": brief file, report file, diff file. This is a deliberate token-cost and compaction-survival design, not just hygiene.
- Reviewer tier routing is by role and diff risk, decided by the controller at dispatch time; there is no routing table keyed to a portable "tier" vocabulary shared across skills.
- The user's only run-time decision points are: approve the design doc, review the plan and pick execution mode, and the finish menu. Mid-run user interaction is suppressed by design.

## 4. Verification and TDD enforcement; wording strength; anti-rationalization techniques

### Takeaway
Enforcement is by strongly worded "Iron Law" blocks, rationalization tables, red-flag STOP lists, and "violating the letter is violating the spirit" framing, validated against pressure scenarios (writing-skills treats skills themselves as TDD'd). There are hard gates in brainstorming (no building before design approval), finishing (menu only after green suite), SDD (no next task with open Critical/Important findings) and a five-round circuit breaker. Enforcement is prose and agent discipline, not tooling, apart from helper scripts for ledgers and diffs.

### Cited Findings
- TDD Iron Law: `NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`; "Write code before the test? Delete it. Start over." with "No exceptions: Don't keep it as 'reference'... Delete means delete"; exceptions only with the human's permission (throwaway prototypes, generated code, config files) — [skills/test-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md)
- TDD "Verify RED - Watch It Fail" is marked "MANDATORY. Never skip."; the project's whole suite (not just the new test file) defines green and failures must be named in the report, including ones the agent did not cause — [skills/test-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md), [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md) (v6.4.1)
- TDD has a 11-row "Common Rationalizations" table ("Too simple to test", "I'll test after", "Already manually tested", "Deleting X hours is wasteful", "TDD will slow me down"...), a 13-item "Red Flags - STOP and Start Over" list ("All of these mean: Delete code. Start over with TDD."), a Verification Checklist ("Can't check all boxes? You skipped TDD. Start over."), and a Good/Bad test example pair — [skills/test-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md)
- `writing-good-tests.md` rules: name the production change that would make the test fail before writing it; assert real behavior not mock behavior; keep test-only code out of production classes; understand a dependency's side effects before mocking — [skills/test-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md)
- verification-before-completion Iron Law: `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`; 5-step gate (IDENTIFY command, RUN full, READ output and exit code, VERIFY, ONLY THEN claim); "Skip any step = lying, not verifying"; table of claim vs required evidence vs insufficient evidence (e.g. "Agent completed" requires VCS diff, not the agent's report; "Requirements met" requires line-by-line checklist, not passing tests); red flags such as "should", "probably", premature "Great!/Done!"; rationalization table ("I'm confident" -> "Confidence is not evidence") — [skills/verification-before-completion/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md)
- systematic-debugging Iron Law: `NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`; four phases; instrumentation at each component boundary; after 3 failed fixes STOP and "question the architecture" and discuss with the human before fix #4; has red-flags list, "your human partner's Signals You're Doing It Wrong" and an 8-row rationalization table. Support files: root-cause-tracing, defense-in-depth, condition-based-waiting, find-polluter.sh — [skills/systematic-debugging/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)
- Brainstorming hard gate: `<HARD-GATE>` block: "Nothing gets built until your human partner approves the design doc" — building includes product code, scaffolding, installing dependencies, creating projects, invoking an implementation skill; after approval the next step is writing-plans "and no other skill". Exceptions: user opt-out and approved throwaway spike. Has its own 6-row red flags table ("They said 'sounds good'" -> "Approval covers what you showed them") — [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- Other tables of rationalizations: SDD ("Close enough on spec compliance", "I'll fix it myself, dispatching is overhead", "The fix was small, skip the re-review"...), executing-plans ("The plan's code is right, skip watching the test fail", "Subagents are slow and expensive, I'll skip the final review too"), using-git-worktrees, requesting-code-review — [skills/subagent-driven-development/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [skills/executing-plans/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md), [skills/using-git-worktrees/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/using-git-worktrees/SKILL.md), [skills/requesting-code-review/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md)
- Evidence-based review: reviewers are told the implementer's report is "unverified claims" and rationales do not downgrade severity; tests output must be "pristine" and warnings are findings — [skills/subagent-driven-development/task-reviewer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md)
- writing-skills formalizes the technique: classify the baseline failure first; "Prohibition + rationalization table + red flags" is the right form for rules agents know but violate under pressure, soft guidance ("prefer...", "consider...") is the wrong form; pressure scenarios combine time + sunk cost + exhaustion; "If you didn't watch an agent fail without the skill, you don't know if the skill teaches the right thing" — [skills/writing-skills/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)
- The repo has a `tests/` tree with suites per harness and per concern (explicit-skill-requests, skill-size, skill-layout, sdd-helper-paths, writing-skills, systematic-debugging, etc.), including a size test that fails when any SKILL.md reaches 20,000 bytes (Claude Code truncates re-attached skills at 20k chars after compaction) — [tests/](https://github.com/obra/superpowers/tree/main/tests), [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md) (v7.0.1)
- Release notes report blind-graded eval numbers for behavior changes (e.g. brainstorming skipped the design doc in 24 of 24 runs before v7.0.1 and 3 of 24 after; filler questions 41 -> 23) — author-reported — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- Recent softening of tone in some places: v6.x/7.x added a "positive instruction redesign" spec and rewrote brainstorming and plan-writing in plainer, less all-caps language; the strongest all-caps/Iron-Law style remains in TDD, verification, debugging and using-superpowers — [docs/superpowers/specs/2026-06-10-positive-instruction-redesign-design.md](https://github.com/obra/superpowers/blob/main/docs/superpowers/specs/2026-06-10-positive-instruction-redesign-design.md) (title only; I did not read its body), [skills/brainstorming/SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)

### Inferences
- "Hard gates" are of two kinds: human-approval gates (brainstorming design approval, plan review, finish menu) and evidence gates (watch the test fail, run the verification command in the same message, green suite before finish menu). Neither is machine-enforced; the ledger and diff scripts are the only mechanical aids.
- The pervasive three-part pattern (Iron Law code block + red flags list + rationalization table) is the portable idiom a catalog author can compare against their own.

### Gaps
- I did not verify that agents actually obey these gates in the field; only author-published eval numbers were found, not independent measurements.
- I did not read the body of the positive-instruction-redesign spec, so the characterization of tone changes is partly inference.

## 5. Post-implementation record of state, decisions, architecture

### Takeaway
No. Superpowers persists no post-implementation record of the resulting state, decisions or architecture. The design doc and plan are pre-implementation artifacts committed before work; the SDD/executing-plans ledger (with rulings, parked findings, deferred minors) is deleted at the end of the run, and the only durable record is git history. Rulings and deferred minors are reported in the final chat message only.

- finishing-a-development-branch only verifies tests, offers merge / PR / keep, and cleans the worktree; it contains no step that writes or updates documentation, an architecture/state file, a changelog or an ADR.
